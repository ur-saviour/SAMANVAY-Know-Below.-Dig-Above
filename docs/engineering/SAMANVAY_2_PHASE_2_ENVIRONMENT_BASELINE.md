# SAMANVAY 2.0 — Phase 2 Environment Baseline

**Status:** In progress  
**Scope:** Reproducible development and test environment  
**Safety boundary:** This phase does not modify production database records, production policies, or production Edge Functions.

## Verified baseline

- The application source is Flutter/Dart under `app/`.
- Android and browser builds are generated by separate GitHub Actions workflows.
- Both workflows currently use Flutter `3.38.0` and create temporary Flutter scaffolding during CI.
- Both workflows install dependencies with `flutter pub add`; therefore the repository does not yet contain a canonical root `pubspec.yaml` and committed `pubspec.lock`.
- The browser build obtains Supabase URL, publishable key, and MapTiler key from GitHub Actions secrets.
- The current production Supabase project is healthy, but its existing development branch was previously observed in `MIGRATIONS_FAILED` state.

## Phase 2 work sequence

1. Preserve the existing Alpha branch and use a dedicated engineering branch for changes.
2. Keep production read-only while the staging strategy is evaluated.
3. Establish a canonical Flutter dependency manifest and lockfile, then make Android and Web workflows consume the same dependency graph.
4. Add a clean-checkout build that does not rely on untracked local files.
5. Provision an isolated Supabase development branch only after its recurring cost is explicitly accepted.
6. Replay and verify migrations on staging; do not merge or reset the production database as a shortcut.
7. Add database-backed integration tests and role-session tests against staging.
8. Retain physical Android and browser acceptance as separate release gates.

## Staging database cost gate

Supabase returned a development-branch estimate of **US$0.01344 per hour** for this project. This is a recurring hourly estimate, not a one-time fee. A staging branch has not been created. Creation requires explicit user approval of this cost.

The existing failed preview branch must not be treated as a passing test environment. Do not delete, reset, or merge it as part of this baseline task.

## Exit criteria

- [ ] Canonical root `pubspec.yaml` committed.
- [ ] Canonical `pubspec.lock` committed and generated by the pinned Flutter SDK.
- [ ] Android and Web builds consume the same committed dependency graph.
- [ ] A clean checkout can reproduce both builds.
- [ ] Isolated staging project/branch exists with migration history verified.
- [ ] Production remains unchanged by staging tests.
- [ ] Automated staging smoke tests cover authentication, RLS, spatial RPCs, and workflow transitions.
- [ ] Physical-device acceptance evidence is recorded.

## Current decision

Do not replace Flutter/Supabase/PostGIS. Stabilize the existing stack first. Introduce a specialist Python/OR-Tools service only when joint-work optimization reaches its implementation phase and has measurable constraints that justify a separate service.
