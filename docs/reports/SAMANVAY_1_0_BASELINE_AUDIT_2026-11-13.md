# SAMANVAY 1.0 — Baseline Engineering Audit

**Audit date:** 13 November 2026  
**Repository:** `ur-saviour/SAMANVAY-Know-Below.-Dig-Above`  
**Baseline branch:** `feature/alpha-03-integrated-platform`  
**Professionalisation branch:** `feature/samanvay-1.0-professionalisation`  
**Audited application source:** `app/main.dart` (blob `b7cbb81433d51911b329383550f6f235ff6f58c8`)  
**Scope:** source inspection, existing readiness/security/GIS reports, latest Android workflow artifact and APK archive integrity. This is a baseline audit, not a production certification or physical-device acceptance.

## Executive finding

SAMANVAY is an existing Flutter + Supabase + MapLibre application with substantial implemented functionality. It is not a blank project and should not be recreated. The latest recorded Alpha 0.3 Android release pipeline completed successfully, and the downloaded ARM64 APK passed an independent ZIP/CRC and required-entry check in addition to the CI package/signature/alignment checks.

The product is **not yet SAMANVAY 1.0**. The main release blockers are device-level acceptance, true end-to-end account/role testing, live operational lifecycle coverage, verified underground GIS data, security-setting closure, deterministic builds and a persistent production signing key.

No application source or live Supabase production data was modified during this baseline audit. A separate professionalisation branch was created as the rollback boundary.

## 3. Architecture and reproducibility findings

1. The repository does not contain a conventional checked-in Flutter project root with a pinned `pubspec.yaml`. The Android workflow generates a Flutter scaffold and adds dependencies during CI. This makes dependency resolution less deterministic than a committed manifest and lockfile.
2. CI runs Dart analysis with non-fatal warning/info flags. The 25 contract checks are source-string and asset-contract checks, not Flutter widget tests, integration tests or real authentication tests.
3. The Android package validator checks the generated manifest, permissions, callback scheme and launcher resources. This is useful but cannot establish installation or runtime behaviour.
4. Existing modules are concentrated in a large `app/main.dart` file with supporting page modules. Before broad refactoring, introduce a tested module boundary incrementally; do not replace the app wholesale.
5. The product depends on external map tiles, SMS/email delivery, Supabase services and other hosted endpoints. Runtime availability, usage policies, provider configuration and error presentation need explicit acceptance tests.

## 4. Security and data-governance findings

- The source uses a Supabase publishable key; service-role credentials must remain server-side. Build-time MapTiler key handling must be treated as a public client key and configured with provider restrictions where supported.
- The latest reported Supabase advisor snapshot identified 16 authenticated-executable SECURITY DEFINER warnings and disabled leaked-password protection. Catalog review found fixed search paths and caller-identity checks in inspected functions, but this is not a complete authorization certification.
- Exact underground geometry is kept server-side. Public users receive generalized coverage only; the department endpoint is constrained to verified assets owned by the authenticated officer’s department.
- Imported utility data must remain `unverified` until the asset owner supplies authority, provenance, source date, spatial reference, accuracy and evidence. Empty GIS results do not mean the location is utility-free or safe to excavate.
- Case attachments have client-side SHA-256 metadata; independent server-side verification and append-only review/audit history remain open.
- Groundwater archive validation is designed to run manually against disposable local PostgreSQL. No restoration to production is authorised by this audit.

## 5. Priority remediation backlog

### P0 — release integrity and user-facing correctness
1. [x] Corrected the displayed tagline to **Know Below. Dig Above.** without altering the original logo SVG.
2. [x] Reduced the opening sequence from approximately 13.8 s to approximately 6.0 s while retaining the logo reveal and flag transition; the ambient controller stops when entering AuthGate.
3. Fix light-mode foreground/background combinations using semantic theme colours; remove hard-coded white-on-white/dark-on-dark text.
4. Perform clean-install and upgrade installation tests on supported Android devices; test startup, login, profile routing, map tile loading, GPS and logout/restart.
5. Produce a production signing plan with an owner-controlled keystore and secret handling before calling any APK a production release.

### P1 — authentication, operations and security
1. Verify actual SMS OTP delivery and signup/login/recovery on a test number; confirm the Supabase Auth phone configuration and rate limits.
2. Test Citizen, Officer, Coordinator and Administrator sessions independently against RLS and server RPCs; verify unassigned departments and self-role changes are denied.
3. Complete ordinary case-evidence server-side integrity verification, provenance metadata, reviewer decisions and append-only history.
4. Review each authenticated SECURITY DEFINER function’s EXECUTE grants, actor checks, object ownership and role paths. Enable leaked-password protection in Supabase Auth and re-run advisor checks.
5. Exercise permit, inspection, coordination, restoration and notification lifecycles with controlled test records.

### P2 — GIS, data and performance
1. Run satellite/vector tile, location permission, viewport refresh, map search, 2D/3D and layer-toggle tests on physical devices.
2. Keep the synthetic cutaway distinct from operational PostGIS layers; test that empty/unverified data never implies safety clearance.
3. Obtain owner-authorised, surveyed utility geometry and evidence before claiming operational underground coverage.
4. Reconcile State/District/ULB/Ward references with current authority sources; keep unmapped or unverified records visibly marked.
5. Measure startup, map frame pacing, memory, CPU, network requests and battery; tune repeating animations and realtime reload patterns from measurements.
6. Add deterministic dependency pins/lockfile and Flutter widget/integration tests; make warnings actionable rather than silently non-fatal.
